# OTA speed: raise the bootloader's BLE MTU

## TL;DR

A full firmware OTA over BLE currently takes ~20 minutes. The cause is **not** the
app — it's that the device's **bootloader fixes its BLE ATT MTU at 23 bytes**, so
each flash row must be sent as ~40 tiny packets. Raising the bootloader's MTU to
247 (or 512) cuts that to ~2–3 packets per row — roughly **13–20× fewer packets**
— bringing a full update down to about **1–2 minutes** (CySmart-class).

**No app change is needed.** The app already negotiates the largest MTU the
device will grant and sizes its DFU packets to it automatically. Raise the MTU in
firmware and the app gets faster on its own.

## Why it's slow today

- The device runs the Cypress `cy_bootload` BLE bootloader. Its BLE component is
  configured with a fixed GATT MTU of 23:

  ```c
  // Firmware/Bootloader/Bootloader_BLE_App101.cydsn/BLE_config.h  (generated)
  #define CY_BLE_CONFIG_GATT_MTU   (0x0017u)   // 23
  #define CY_BLE_CONFIG_L2CAP_MTU  (23u)
  ```

- At MTU 23 the usable ATT write payload is `MTU − 3 = 20` bytes. After the 7-byte
  DFU packet framing, only **13 data bytes** fit per packet.
- A PSoC6 flash row is **512 bytes**, so each row needs ~39 `SendData` packets
  plus one `ProgramData` ≈ **40 packets/row**. The image is **966 rows** ≈
  **38,600 packets**, each a BLE round-trip.
- We must send them serially (one packet, wait for its status notification, next).
  Pipelining (firing several without waiting) was tried and **deterministically
  corrupts the bootloader's receive buffer** once a row's burst grows — the device
  reports `ERR_CHECKSUM` near the end of a row, and Sync+retry can't recover it.
  This is a limitation of the phone BLE stack + this bootloader, so the reliable
  path is serial. CySmart is fast because it runs on a PC BLE controller with
  proper write flow control **and/or against a larger MTU.**

## The fix (firmware)

Raise the bootloader's GATT MTU. **This is a change to the bootloader project, not
the app.**

### What to change

In **PSoC Creator**, open the bootloader project
(`Bootloader/Bootloader_BLE_App101.cydsn`):

1. Open the **BLE component** customizer → **GATT Settings** (a.k.a. "General" /
   profile settings depending on the PDL version).
2. Set the **GATT MTU size** from `23` to **247** (recommended) or up to **512**.
3. Rebuild the bootloader and **reflash it** to the device (see caveat below).

> Do **not** hand-edit `BLE_config.h`. That file is generated by the BLE component
> customizer and will be overwritten on the next build. Change the value in the
> customizer so `CY_BLE_CONFIG_GATT_MTU` regenerates to the new value.

While you're in the BLE/GAP settings, also consider tightening the **preferred
GAP connection interval** (e.g. min 7.5 ms / max 15 ms). The central can only go
as fast as the peripheral's accepted connection parameters, so a faster interval
compounds the MTU win.

### No bootloader buffer change needed

The bootloader's command/data buffers are already sized for a full row plus
overhead:

```c
#define CY_BOOTLOAD_SIZEOF_CMD_BUFFER  (CY_FLASH_SIZEOF_ROW + 16u)  // 528
#define CY_BOOTLOAD_SIZEOF_DATA_BUFFER (CY_FLASH_SIZEOF_ROW + 16u)  // 528
```

The largest packet at MTU 512 is ~509 bytes, which fits within 528.

## Expected impact

| Device MTU | Data bytes/packet | Packets/row | Total packets | Est. full update |
| ---------: | ----------------: | ----------: | ------------: | ---------------: |
|         23 |                13 |        ~40  |      ~38,600  |        ~20 min   |
|        247 |               237 |         ~3  |       ~2,900  |       ~1.5 min   |
|        512 |               502 |         ~2  |       ~1,900  |        ~1 min    |

(Row count 966; serial transfer. Times are approximate and scale with the
connection interval.)

## Caveat: reflashing the bootloader

The bootloader is the immutable part of the device — it is what *performs* OTA
updates, so it cannot update itself over the air. Raising its MTU requires
**reprogramming the bootloader via a hardware programmer** (e.g. MiniProg / KitProg)
on existing units. New production units would ship with the updated bootloader.

The application image is unaffected: existing `.cyacd2` images keep working with
the new bootloader, just faster.

## Verifying after the change

The app logs the negotiated MTU at the start of a transfer:

```
[OTA] Using MTU 247 (max write 244 bytes)
```

(See `lib/ota/ota_service.dart`.) If that still shows 23, the new MTU didn't take
effect — confirm the bootloader (not just the app image) was reflashed and that
the BLE customizer value regenerated into `BLE_config.h`.

## App side (already done — for reference)

- `OtaService.flashImage` calls `device.requestMtu(517)` and passes the granted
  MTU to the transfer.
- `DfuTransfer` derives its packet size from the MTU (`_maxPacket = MTU − 3`) and
  chunks every row to fit a single write, so it transparently uses larger packets
  as soon as the device grants a larger MTU. No app change is required for the
  speedup.
- `DfuTransfer.inFlightWindow` defaults to `1` (serial). It is left tunable for a
  future device whose bootloader/stack can sustain pipelined writes, but should
  stay at `1` on the current MTU-23 bootloader.
